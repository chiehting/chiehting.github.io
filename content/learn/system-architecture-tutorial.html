Preface前言與閱讀方式

架構不是一份藍圖，而是一連串被流量逼出來的決策。每一個階段的架構，都是為了解決前一階段撞到的瓶頸而生；同時它也一定會製造出新的問題。這份教程就是照這個因果鏈排列的。

每一章的結構固定如下：

  • 情境 — 什麼樣的流量與業務規模會走到這一步。
  • 架構圖 — 這個階段的元件與資料流向。
  • 關鍵元件 — 中英對照的名詞表與各自的職責。
  • 為什麼這樣做 — 這個結構解決了什麼、代價是什麼。
  • 瓶頸 / 何時進入下一階段 — 觸發下一次演進的訊號。
  • 延伸議題 — 採用這個架構後，軟體端必須額外處理的問題清單。
關於「延伸議題」

每章結尾的延伸議題只列名稱、不展開內容，這是刻意的。這份教程聚焦在架構層面；那些名詞屬於「選了這個架構之後，程式碼要面對的帳單」。例如導入快取後會出現快取擊穿 (Cache Breakdown)，但本文不討論它怎麼解，只提醒你它存在。把它當成後續各自深挖的索引。

最重要的一句話

不要跳級。每個階段的複雜度成本都是真實的——監控、部署、除錯、人力。沒有撞到瓶頸就導入下一階段，等於用確定的複雜度去換不確定的擴展性。絕大多數系統終其一生停在 S2–S4 就完全足夠。

Framework三個貫穿全文的座標軸

在進入階段之前，先建立三組會反覆出現的判斷基準。後面每一章的取捨，本質上都是在這三個軸上移動。

軸一：擴展的方向

中文英文做法天花板
垂直擴展Vertical Scaling / Scale-up把單台機器換得更強（CPU、RAM、NVMe）單機規格上限；停機升級；價格對效能非線性

原則：先垂直、後水平。垂直擴展幾乎不需要改程式，是最便宜的一步；水平擴展則要求架構本身先具備可分散的性質。

軸二：流量的三種形狀

形狀英文特徵主要對策
低流量Low Traffic單機資源長期閒置簡單為上，垂直擴展

關鍵區別

持續高流量是容量問題，可以靠加機器解決；瞬間高流量是時間問題——擴容速度趕不上流量爬升速度。這就是為什麼 S7 用的手段（限流、排隊、預先靜態化）和前面幾章的邏輯完全不同：前面在「增加供給」，S7 在「管理需求」。

軸三：狀態放在哪裡

幾乎所有擴展的困難都源自狀態 (State)。無狀態的東西可以無限複製，有狀態的東西不行。整份教程可以視為一場持續的行動：把狀態從應用程式裡一層層擠出去，集中到少數幾個專門處理狀態的元件（快取、資料庫、訊息佇列），再想辦法讓那些元件自己也能擴展。

為什麼從這裡開始

單體不是過渡期的妥協，而是正確的預設選擇。它把跨模組呼叫變成函式呼叫——沒有網路延遲、沒有部分失敗 (Partial Failure)、沒有分散式追蹤的需求。一個交易可以包住整段業務流程，一致性由資料庫免費提供。除錯時 stack trace 是完整的。

這個階段的擴展手段就是垂直擴展：機器升一級。在雲上這通常是幾分鐘的停機，成本遠低於任何架構改造。同時也應該先把最便宜的效能功課做完：資料庫索引、N+1 查詢、連線池設定、開啟 Gzip/Brotli 壓縮。這些調校往往能帶來比架構改動更大的效益。

瓶頸：何時該離開 S0

  • 單點故障 (Single Point of Failure, SPOF) — 機器一掛，全站消失；部署必然造成停機。這通常是離開 S0 的第一個理由，而且與流量無關。
  • 資源互相搶奪 — 資料庫的 I/O 尖峰拖垮應用程式的回應時間，兩者無法獨立調校。
  • 垂直擴展碰壁 — 已經是可負擔範圍內最大的機型。
  • 本地磁碟綁死 — 使用者上傳的檔案存在本機，讓「再開一台」變成不可能。

關鍵動作：無狀態化 (Statelessness)

「無狀態」不是說應用程式不處理狀態，而是說任何一台應用伺服器都能處理任何一個請求，且結果相同。這是水平擴展的前提條件。實務上要處理四類藏在行程裡的狀態：

行程內快取In-process Cache可保留，但必須容忍各節點資料不一致

為什麼這樣做

分層帶來三個獨立性：獨立擴展（Web 層與資料層的資源需求形狀不同）、獨立調校（資料庫機器可以配大量記憶體給 buffer pool，應用機器配 CPU）、獨立故障域（應用程式的記憶體暴衝不會直接拖垮資料庫）。

更重要的是，這一步的真正產出不是效能，而是可能性：完成無狀態化之後，「多開一台」從架構改造變成了設定調整。

瓶頸：何時該離開 S1

  • 單台應用伺服器的 CPU 或並發連線數飽和。
  • 應用層仍是單點故障，無法做到零停機部署。
  • 網路延遲成為新變數：原本的函式呼叫變成跨機器往返。

P2C 的實作細節

P2C 的做法是隨機抽兩台，再從這兩台中選連線數較少者。Nginx 以 random two least_conn; 提供，文件直接引用 Azar/Karlin 的 balls-into-bins 論文[1]。Envoy 的 least request 在權重相等時同樣採用 P2C，抽樣數 choice_count 預設為 2，文件引用 Mitzenmacher 的結果稱其「接近 O(N) 全掃描的效果」，並特別指出 P2C 具備抗羊群效應 (resistance to herding behavior) 的性質[2]。

純 least_conn 在多個負載平衡器並存時的問題正在於此：每台 LB 各自看到「同一台最閒」，於是一起把流量灌過去。P2C 用隨機性打破了這種同步。

一個常見誤解

Nginx 的 hash 指令預設不是一致性雜湊。文件明確警告：增減一台伺服器「may result in remapping most of the keys to different servers」。必須加上 consistent 參數才會啟用 ketama 一致性雜湊，此時「只有少數 key 會被重新映射」[1]。用於快取親和性時，這個差別決定了擴容當下是損失少量命中率，還是快取整體失效。

健康檢查與故障隔離

負載平衡器的價值有一半來自健康檢查 (Health Check)：定期探測後端，把失敗節點移出輪替。實務上要區分兩種探針——存活探針 (Liveness Probe) 判斷「要不要重啟」，就緒探針 (Readiness Probe) 判斷「能不能接流量」。兩者混用是常見錯誤：暖機中的節點應該是「未就緒」而非「已死亡」。

多層入口：DNS 與 Anycast

負載平衡器自己也是單點。實務上再往前疊一層：DNS 輪詢 (DNS Round Robin) 或 Anycast 把流量分散到多個 LB 或多個地理區域。要注意 DNS 層的分流受 TTL 與各級解析器快取影響，故障切換不即時，因此它是「地理／區域級分流」的工具，不是「秒級故障轉移」的工具。

大規模的實際樣貌：Google Maglev

Google 的 L4 負載平衡器 Maglev 是這套設計的具體範例，論文揭露的事實[3]：它跑在一般商用 Linux 伺服器上而非專用硬體；路由器透過 ECMP (Equal Cost Multipath) 把封包平均送到各 Maglev 機器；單台機器能以小封包打滿 10Gbps 連線；並以一致性雜湊搭配連線追蹤 (Connection Tracking) 來降低節點增減對連線導向協定的衝擊。自 2008 年起服務 Google 的流量。

論文列出傳統硬體 LB 的四項限制，正好說明了為何要走軟體路線：單機容量上限、僅 1+1 冗餘、缺乏可程式性、擴容須採購與實體部署。

瓶頸：何時該離開 S2

  • 應用層再加機器已無效——回應時間由資料庫決定。
  • 資料庫連線數被大量應用節點撐爆。
  • 同樣的查詢在不同節點上被重複執行成千上萬次。

資料新鮮度 (Freshness) 與一致性

絕大多數線上系統的讀寫比極度傾斜。既然同一份資料被反覆讀取，就沒有理由每次都讓資料庫重新計算一次。快取的本質是用「資料可能過期」換取「延遲與吞吐」——這個交換是否划算，取決於業務能容忍多舊的資料。

快取的兩個治理決策

逐出策略 (Eviction Policy)：記憶體滿了要丟誰——LRU（最近最少使用）、LFU（最不常使用）、隨機、或直接拒絕寫入。過期時間 (TTL)：資料能舊到什麼程度。這兩項應該是每個快取鍵的明確設計，而非預設值。

逐出策略的實際行為（以 Redis 為例）
  • maxmemory 在 64 位元系統上預設為 0，即不限制。不設定它，逐出策略永遠不會生效[4]。
  • volatile-* 系列策略在沒有任何 key 設定 TTL 時，行為等同 noeviction——也就是直接開始回報寫入錯誤。這是實務上常見的踩雷點。
  • Redis 的 LRU 是近似的，不是真 LRU：它隨機取樣少量 key，逐出其中最久未存取者。取樣數由 maxmemory-samples 控制，預設 5；提高到 10 會非常接近真 LRU，代價是額外 CPU。
  • LFU 同樣是近似的，使用 Morris counter；預設「約一百萬次請求飽和計數器、每一分鐘衰減一次」。
  • 複製與持久化的緩衝區記憶體不計入 maxmemory。設定上限時應預留 RAM，否則實際用量會超出你以為的上限。
HTTP 快取指令的出處，常被搞混

RFC 9111 (HTTP Caching) 定義的回應端 Cache-Control 指令是：max-age、s-maxage、no-cache、no-store、no-transform、private、public、must-revalidate、proxy-revalidate、must-understand[5]。

常被誤認為屬於 RFC 9111 的兩個指令其實不在其中：stale-while-revalidate 來自 RFC 5861[6]，immutable 來自 RFC 8246[7]。另外 s-maxage 與 proxy-revalidate 只對共享快取 (Shared Cache) 生效，對私有快取無效。

請求合併：架構層就能擋掉快取踩踏

快取失效瞬間大量請求同時回源，是尖峰場景最常見的崩潰原因之一。這在代理層就有現成機制，不必等到應用層才處理。以 Nginx 為例[8]：

  • proxy_cache_lock（預設 off）— 開啟後同一時間只允許一個請求回源填充該快取項，其餘請求等待結果。這就是請求合併 (Request Coalescing)。
  • proxy_cache_lock_timeout（預設 5s）— 等待逾時後請求會被放行到上游，但該回應不會被寫入快取。
  • proxy_cache_use_stale updating — 在快取項更新期間先回傳舊內容，避免回源風暴。
  • proxy_cache_background_update（預設 off）— 回傳舊內容給使用者的同時，在背景發子請求更新。必須同時設定 proxy_cache_use_stale updating 才生效。

瓶頸：快取解決不了什麼

  • 寫入流量 — 快取只擋讀，寫入仍然全數壓向資料庫。
  • 低命中率的長尾 — 若每個使用者查的都是不同資料，快取幾乎無效。
  • 快取失效瞬間的衝擊 — 大量請求同時穿透到資料庫（這正是下方延伸議題的重點）。
  • 資料量本身 — 單表資料成長到索引無法有效工作的規模。

應用層可以無限複製，是因為它無狀態。資料庫不行。因此資料庫擴展是一連串逐步放棄保證的過程：先放棄「讀到最新資料」，再放棄「跨資料的交易」，最後放棄「跨資料的關聯查詢」。每一步都應該在前一步真的撐不住時才走。

這是投資報酬率最高的一步：讀取容量隨從庫數量增長，而寫入路徑完全不動。核心代價是複製延遲 (Replication Lag)——剛寫入的資料可能在從庫上讀不到，也就是說系統從此進入最終一致性 (Eventual Consistency)。應用程式必須明確標記哪些讀取「必須讀主庫」（例如使用者剛送出表單後看到的頁面）。

4.2 垂直分庫 (Vertical Partitioning)

按業務領域把表拆到不同資料庫實例：使用者庫、訂單庫、商品庫。每個庫各自擁有完整的主從結構。這一步相對安全，且天然對應後續的服務拆分 (S6)。代價是跨庫 JOIN 消失，必須改由應用層組裝資料。

4.3 水平分片 (Sharding / Horizontal Partitioning)

同一張表按某個分片鍵 (Shard Key) 切成多份，分散到多個實例。這是唯一能同時擴展寫入量與資料量的手段，也是複雜度最高的一步。

Abadi 在提出 PACELC 的論文中，主張 CAP 對現代分散式資料庫設計的影響「比一般認知的更為有限」，因為「CAP 只在特定類型的故障面前施加限制，並未約束系統在正常運行下的任何能力」。他認為許多設計者誤以為 CAP 也管正常運行，因而做出「不必要地受限的系統」[9]。

假設訊息一定會重複投遞，因此所有消費者邏輯都必須是冪等 (Idempotent) 的——同一則訊息處理一次和處理十次，結果必須相同。與其追求 Exactly-once 的傳輸保證，不如在業務層做到「重複執行無害」，這在工程上更可靠也更便宜。

投遞保證需要整組設定才成立（以 Kafka 為例）

「開了冪等就安全」是危險的簡化。Kafka 的設定之間存在強耦合[10]：

  • Kafka 3.0 起 enable.idempotence 預設為 true，且 acks 預設從 1 改為 all。
  • 冪等性成立的前提是三個條件同時滿足：acks=all、retries > 0、max.in.flight.requests.per.connection ≤ 5。
  • 設定衝突時的行為是分歧的：若設了衝突值但未顯式開啟冪等，冪等性會靜默停用；若顯式開啟又設了衝突值，則直接拋出 ConfigException。換句話說，單獨把 acks 調成 1 會讓你在毫無警告的情況下失去冪等保證。
  • 耐久性的建議組合是 replication factor = 3 + min.insync.replicas = 2 + acks=all。

這個例子的通則是：投遞保證是整個設定組合的性質，不是單一開關。無論用哪套訊息系統，都應該實際驗證而非假設。

7.1 為什麼前面六章不夠

前六章解決的是容量問題：流量成長是可預測的，可以提前加機器。瞬間高流量是時間問題——流量爬升的速度遠快於任何擴容機制的反應速度。

手段為何在瞬間尖峰下失效
自動擴縮容 Autoscaling反應式擴容需要「觀察指標 → 決策 → 啟動實例 → 暖機 → 通過健康檢查」，整條鏈路是分鐘級的；而尖峰是秒級的。等新機器就緒時，系統已經倒了
快取 Cache尖峰通常集中在極少數熱點資料上，形成單一熱點 Key；且活動開始瞬間的快取失效會讓所有請求同時穿透
資料庫分片 Sharding秒殺的庫存往往是同一列資料，無論分幾片都落在同一個分片、同一行鎖上
加機器 More Servers成本按尖峰配置意味著平時 95% 的資源閒置；且資料庫的單點寫入無法靠加應用機解決

即使擴容方向的穩定視窗預設為 0（可立即反應），指標仍是每 15 秒才採樣一次；新 Pod 還要經過 30 秒初始就緒延遲，CPU 指標則有 5 分鐘的初始化期間不被採信。再加上拉取映像檔、行程啟動、JIT 暖機、連線池建立——整條鏈路是數十秒到數分鐘級。

而秒殺的流量爬升是秒級。這就是為什麼 S7 的答案是排程式擴容 (Scheduled Scaling) 加預熱，而不是依賴反應式擴容。

核心心法

把流量像漏斗一樣逐層過濾，讓真正抵達核心資源的請求數量，是一個你事先決定好的常數。一百萬人搶一千件商品，只需要放一小部分請求進入下單邏輯——其餘的應該在越早、越外層的地方被擋下越好。每往內一層，請求的處理成本就貴一個數量級。

7.3 限流 (Rate Limiting)

限流是漏斗的核心機制：明確定義系統每秒願意接受多少請求，超出的部分立即拒絕。快速拒絕（返回 429）遠優於讓所有請求一起慢慢逾時——後者會耗盡連線與執行緒，把局部過載變成全站癱瘓。

429 Too Many Requests 由 RFC 6585 定義，語意是「使用者在給定時間內送出了過多請求（限流）」。回應可以（MAY，非強制）帶 Retry-After 標頭告知等待時間，且 429 回應 MUST NOT 被快取儲存[12]。RFC 刻意不規範如何識別使用者或如何計數——限流的維度完全由實作決定。

值得注意的是 RFC 自己的安全性註記：伺服器沒有義務回 429，因為在攻擊期間為每個請求產生回應本身就在消耗資源，直接斷開連線可能是更好的選擇。這正是「負載卸除 (Load Shedding)」的論據——在極端過載下，連拒絕都要花錢。

限流的維度與部署位置

  • 維度：全域總量、單一 IP、單一使用者、單一 API、單一租戶。真實系統通常同時套用多層，最嚴格者生效。
  • 單機限流 (Local Rate Limiting)：無網路開銷、無單點，但無法精準控制叢集總量（總量 = 單機閾值 × 節點數，節點數變動時失準）。
  • 分散式限流 (Distributed Rate Limiting)：以 Redis 等集中式計數器控制叢集總量，精準但每次請求多一跳，且限流器本身成為關鍵路徑上的相依。
  • 混合式：本地令牌桶處理絕大多數請求，定期向中央配額服務批次領取額度。這是大規模系統的常見折衷。

7.4 過載保護：熔斷、艙壁、降級

限流管的是「進來多少」，過載保護管的是「壞掉之後怎麼辦」。目標是阻止局部故障擴散成全域故障。

重試是尖峰時最危險的好意

系統一慢，客戶端與中間層開始重試，流量瞬間翻倍到數倍，把「有點慢」直接推成「完全掛掉」——這叫重試風暴 (Retry Storm)。三條紀律：指數退避 (Exponential Backoff) 拉開重試間隔；加入抖動 (Jitter) 讓各客戶端的重試時間點隨機化，避免同步湧入形成新的尖峰；限制重試預算 (Retry Budget)，只在整體錯誤率低時才允許重試。另外，呼叫鏈上只在最外層重試一次——若每一層都重試三次，五層深的呼叫鏈會放大成 243 倍。

為什麼「只有指數退避」還不夠

AWS 的實測分析指出：純指數退避只降低了重試的速率，沒有打散重試的分布。因為所有客戶端遵循同一套確定性排程，重試依然以同步叢集的形式抵達——差別只是叢集之間多了空窗期[13]。抖動修正的是分布而非速率，目標是把尖峰平滑成近似定值的速率。

變體英文做法
完全抖動Full Jitter在整個退避區間內完全隨機
等分抖動Equal Jitter保留固定一半、隨機化另一半，避免過短的等待
去相關抖動Decorrelated Jitter隨機上界依前一次抽樣結果成長，而非固定指數排程

模擬結論：無抖動的指數退避在工作量與完成時間上都是「明顯的輸家」；在 100 個競爭客戶端下，加入抖動讓總呼叫次數減少超過一半。Equal Jitter 在三者中最差；Full 與 Decorrelated 是取捨——前者工作量較少，後者完成略快。

但要注意其極限：抖動並未改變根本的擴展性，總工作量仍隨競爭數呈 N² 成長，抖動只是在合理競爭程度下大幅降低常數因子。它是必要的衛生習慣，不是過載的解方——真正的解方仍是限流與負載卸除。

7.6 靜態化與邊緣卸載

尖峰流量中，讀取請求通常佔九成以上——大量使用者在反覆刷新商品頁，真正下單的是少數。因此最高效的一步是把活動頁面完全靜態化，推到 CDN 邊緣，讓這九成流量根本不進入源站。

  • 整頁靜態化 — 活動頁預先渲染為靜態 HTML，動態部分（庫存數、個人資訊）以獨立的輕量 API 補齊。
  • 邊緣快取動態內容 — 即使是庫存數這類會變的資料，設定 1–3 秒的極短 TTL，也能把源站的讀取 QPS 降低數個數量級。
  • 請求合併 (Request Coalescing) — 快取失效瞬間，代理層只放行一個請求回源，其餘請求等待該結果。這是防止快取失效造成源站瞬間過載的關鍵機制。
  • 邊緣運算 (Edge Computing) — 把限流、驗證、A/B 分流、排隊憑證校驗下推到邊緣節點執行。

7.10 事前驗證

上述所有機制都有一個共同前提：必須在真實流量到來之前被驗證過。限流閾值設多少、熔斷什麼時候跳、降級開關能不能一鍵打開——這些都不能靠推測。

  • 壓力測試 (Load Testing) — 找出系統的實際拐點：吞吐停止增長、延遲開始飆升的那個負載。限流閾值應設在拐點之前。
  • 全鏈路壓測 (Full-link Load Testing) — 在生產環境以影子流量與影子資料表施壓，因為瓶頸往往出現在測試環境不存在的地方。
  • 混沌工程 (Chaos Engineering) — 主動注入故障（殺節點、注入延遲、斷網），驗證降級與熔斷確實會如預期觸發。
  • 預案與開關 (Runbook & Feature Flags) — 每個降級動作都要有可即時切換的開關，以及寫好的操作手冊。尖峰當下不是思考的時候。

錯誤預算的原始設計（Google SRE）

Google SRE 對錯誤預算的定義是「一個清楚、客觀的指標，決定服務在單一季度內被允許有多不可靠」[15]。推導只有三步：產品端訂出 SLO；實際可用度「由中立第三方——我們的監控系統——量測」；兩者的差額就是本季剩餘的「不可靠額度」。

書中範例：SLO 為 99.999% 時，該季失敗率預算為 0.001%；某次事故若失敗了 0.0002% 的預期查詢，就消耗掉該季預算的五分之一。

三個容易被忽略、但決定機制成敗的設計：

  • 基礎設施故障消耗同一個預算池——網路中斷、資料中心故障同樣「吃掉錯誤預算」，可能因此壓縮本季剩餘的發布次數。理由是「所有人共同承擔可用性的責任」。
  • 這個機制有前提：它「取決於 SRE 團隊確實擁有在 SLO 被打破時停止上線的權力」。沒有這個權力，錯誤預算只是一張好看的儀表板。
  • 可以反向使用：被擋住無法出貨的團隊「可以選擇放寬 SLO（從而增加錯誤預算）」。這讓「過度追求可靠度」的成本變得顯性且可協商。

書中也自承「發布全停」是粗糙版本，並指出更細緻的做法是隨預算耗盡而逐步減速發布或回滾。

這條演進路徑的每一步，都是拿複雜度去換某種特定的擴展能力。判斷是否該走下一步，唯一的依據是：你是否已經在當前階段撞到了那個具體的瓶頸，並且已經窮盡了更便宜的手段（調校、索引、垂直擴展、刪掉不必要的功能）。架構師的價值不在於能設計出多複雜的系統，而在於知道什麼時候不需要。
