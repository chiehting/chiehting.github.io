階段 0 — 認識這個角色Stage 0 — Understanding the Role

0.1 SRE 是什麼

網站可靠性工程 (Site Reliability Engineering, SRE) 是 Google 於 2003 年由 Ben Treynor Sloss 創立的一套工程實踐。 最常被引用的定義是：

定義 / Definition

"SRE is what happens when you ask a software engineer to design an operations team."

「當你請一位軟體工程師去設計一個維運團隊時，所產生的結果就是 SRE。」

這句話的重點不在「維運」，而在用軟體工程的方法解決維運問題。傳統維運靠「加人」來擴張， SRE 靠「寫程式把人從迴圈裡拿掉」來擴張。這是整個角色的思想源頭，後面所有實踐都是它的推論。

SRE

0.3 SRE 的日常究竟在做什麼

一個常見誤解是「SRE 就是待命救火」。實際上 SRE 有一條著名的紀律：

50% 上限規則 / The 50% Rule

SRE 花在維運工作 (ops work) 的時間必須被限制在 50% 以下， 剩餘時間必須投入工程專案 — 也就是寫程式把維運工作消滅掉。 若某團隊長期超過 50%，多出的工作量會被退回給開發團隊，或增派人力，直到回到平衡。

典型的時間分配：

  • 待命與事件處理 (On-call & Incident Response) — 值班輪值、處理告警、主導事故
  • 可靠性工程 (Reliability Engineering) — 設計評審、容量規劃、韌性改善
  • 自動化 (Automation) — 消除瑣務、建工具、建平台
  • 可觀測性建設 (Observability) — 監控、告警、儀表板、SLO 落地
  • 事後檢討 (Postmortem) — 寫報告、追蹤改善項

0.4 你需要具備的心智模型

可靠性是可以被「花掉」的

100% 可用性既不可能也不划算。可靠性是一個預算，用來換取發布速度。

失敗是常態，不是例外

分散式系統中，部分失敗永遠在發生。設計目標是優雅降級，不是「永不出錯」。

人不該做機器能做的事

重複性的手動操作是瑕疵，不是工作內容。

對事不對人

事故的根因是系統設計，不是「某人按錯按鈕」。

階段 0 驗收

你能用三句話向非技術人員解釋：SRE 跟維運工程師差在哪、為什麼公司需要 SRE、SRE 怎麼衡量自己做得好不好。

階段 1 — 技術地基Stage 1 — Technical Foundations

這是不可跳過的階段。SRE 的價值來自於「當系統壞掉時，你能一路往下追到底」。 沒有地基，你只能重啟服務然後祈禱。

1.1 作業系統與 Linux

目標不是「會用指令」，而是理解作業系統如何調度資源，因為 90% 的線上問題最後都會收斂到 CPU、記憶體、磁碟 I/O、網路這四類資源之一。

必須理解的概念

  • 行程與執行緒 (Process & Thread)、行程狀態、殭屍行程、fork/exec
  • 排程與負載 (Scheduling & Load Average) — 為什麼 load average 高不等於 CPU 忙
  • 記憶體管理 (Memory Management) — 虛擬記憶體、page cache、swap、OOM Killer
  • 檔案系統與 I/O (Filesystem & I/O) — inode、file descriptor、阻塞與非阻塞 I/O
  • 系統呼叫 (System Call) — 使用者空間與核心空間的邊界
  • 命名空間與控制群組 (Namespace & cgroup) — 這是容器的底層原理，第 4 階段會用到
  • 訊號 (Signal) — SIGTERM 與 SIGKILL 的差異（優雅關閉的基礎）

1.2 網路

SRE 面對的分散式系統本質上是「一堆透過網路溝通的行程」。網路知識的深度，直接決定你能不能診斷 「服務沒掛但很慢」這類最難的問題。

必須理解的概念

  • OSI 與 TCP/IP 模型 — 尤其是 L3（IP）、L4（TCP/UDP）、L7（HTTP）的分工
  • TCP 三次交握與四次揮手 (Three-way Handshake / Connection Teardown)、TIME_WAIT 的意義
  • TCP 壅塞控制與重傳 (Congestion Control & Retransmission) — 為什麼丟包會讓延遲暴增
  • DNS 解析流程、TTL、快取 — 大量線上事故的根因
  • TLS 交握 (TLS Handshake)、憑證鏈、憑證過期
  • HTTP/1.1 vs HTTP/2 vs HTTP/3、keep-alive、連線池
  • 負載平衡 (Load Balancing) — L4 與 L7 的差異、健康檢查
  • NAT、防火牆、路由表、子網路劃分 (CIDR)

工具清單

dig / nslookup（DNS）、curl（HTTP 與時間分解）、ss / netstat（連線狀態）、 tcpdump / Wireshark（封包分析）、mtr / traceroute（路徑診斷）、 iptables / nftables（封包過濾）、openssl s_client（TLS 診斷）。

1.3 程式設計能力

關鍵分水嶺

SRE 與傳統維運工程師最大的差別，就是能不能寫出正式的、可維護的軟體。 這不是「會寫 shell script」的程度，而是「能設計並交付一個內部工具或服務」的程度。

  • Python — 自動化、工具、資料處理的通用選擇；標準函式庫、型別註記、測試
  • Go — 雲原生生態的通用語言（Kubernetes、Prometheus、Terraform 皆為 Go 撰寫）； 並行模型 (goroutine/channel)、編譯成單一二進位檔的維運友善性
  • Bash — 黏合層；但要知道什麼時候該停止用 Bash（超過 100 行就該換語言）
  • 資料結構與演算法 — 不需要刷題到競賽水準，但要能分析複雜度、理解雜湊與樹
  • 並行與同步 (Concurrency & Synchronization) — 競態條件、死鎖、鎖的成本
  • 測試 — 單元測試、整合測試；自動化腳本也需要測試

1.4 版本控制與協作

  • Git — 不只是 add/commit/push，而是理解 DAG 模型：分支、rebase、cherry-pick、bisect（找出哪個 commit 引入問題的利器）
  • 分支策略 (Branching Strategy) — trunk-based development、GitHub Flow
  • 程式碼審查 (Code Review) — 這是 SRE 影響系統可靠性最早、最便宜的介入點

2.1 SLI / SLO / SLA — 可靠性的度量三層

SLI — 服務等級指標 (Service Level Indicator)

一個可量測的、反映使用者體驗的數值。標準寫法是一個比例：

SLI = (良好事件數 / 有效事件總數) × 100%

例：成功的 HTTP 請求數 / 全部 HTTP 請求數
例：回應時間 < 300ms 的請求數 / 全部請求數

注意：吞吐量 (throughput) 不在這份官方分類中 — 它是重要的容量指標，但通常不是好的 SLI，因為使用者不會因為「系統每秒處理很多請求」而感到滿意。

為什麼延遲不能用平均值

平均延遲會被大量的快速請求稀釋，完全隱藏尾端問題。務必使用百分位數 (percentile)： p50（中位數）、p95、p99、p99.9。「p99 延遲 2 秒」代表每 100 個請求就有 1 個使用者等了 2 秒。

SLO — 服務等級目標 (Service Level Objective)

對 SLI 設定的目標值 + 時間窗。這是 SRE 團隊的內部承諾，也是所有決策的依據。

過去 28 天內，99.9% 的 HTTP 請求應在 300ms 內成功回應
 └──時間窗──┘  └─目標─┘        └────── SLI 定義 ──────┘

Google 的預設是四週滾動窗口 (four-week rolling window)。 用滾動窗口而非「自然月」，是為了避免每個月一號預算歸零時的行為扭曲。

設定 SLO 的三個原則：

  • 不要追求 100%。SRE Book 的原話是 「100% 幾乎永遠不會是正確的可靠性目標」。理由有二：
    (1) 成本是非線性的 — 可靠性每往上推一級，下一級的改善可能比上一級貴 100 倍；
    (2) 使用者根本感受不到 — 書中的例子是： 「一個用著 99% 可靠度手機的使用者，分辨不出 99.99% 與 99.999% 的服務可靠性差異。」 使用者端的網路、裝置、ISP 本身就是可靠性的天花板。
  • 從使用者旅程出發 (Critical User Journey, CUJ)，不要從機器指標出發。 「CPU 使用率」不是 SLI，因為使用者不在乎 CPU。
  • 從寬鬆開始，逐步收緊。先觀測現況，再訂一個「略優於現況」的目標。

SLA — 服務等級協議 (Service Level Agreement)

對外部客戶的合約，違反時有財務或法律後果（退款、賠償）。 關鍵設計原則：SLA 必須比 SLO 寬鬆。

內部 SLO: 99.9%   ←─ 團隊真正努力達成的目標
外部 SLA: 99.5%   ←─ 對客戶的承諾（留有安全邊際）
                      SLO 破了還有緩衝，不會立刻違約賠錢
反直覺但重要：不要過度達標 (Don't Overachieve)

如果你承諾 99.9% 卻長期跑出 99.999%，下游團隊會開始依賴那個沒被承諾的可靠性， 於是你實際上被鎖死在 99.999%，再也不能承擔任何風險。
Google 對此的做法相當激進：內部鎖服務 Chubby 曾因為太可靠， 而被刻意安排計畫性停機，好讓依賴它的團隊維持正確的失敗處理假設。
這也是 SLA 必須比 SLO 寬鬆的同一個道理 — 可靠性的承諾，講到做到就好，不要超額奉送。

兩種可用性算法

以時間為基礎 (time-based availability) — 正常運行時間 / 總時間，也就是上表的算法。

2.2 錯誤預算 — SRE 最重要的一個發明

錯誤預算 (Error Budget) 是 SLO 的數學補數：

錯誤預算 = 100% − SLO

SLO = 99.9%  →  錯誤預算 = 0.1%
                在 28 天內 ≈ 40 分鐘的不可用時間額度

它的天才之處在於：把「穩定 vs 創新」這個永恆的組織衝突，變成一個雙方都同意的數字。

預算還有剩

  • 盡量發布，加快實驗
  • 可以承擔風險（灰度、新架構）
  • 不必為了求穩而凍結

預算燒完了

  • 凍結功能發布，只允許修 bug 與可靠性改善
  • 所有工程資源轉向穩定性
  • 直到預算回補才解凍

這個「燒完就凍結」的規則要事先寫成錯誤預算政策 (Error Budget Policy)， 並由開發、SRE、產品三方共同簽署。重點不是懲罰，而是事先約定好，事發時不必吵架。

SRE Workbook 附錄 B 的官方範例政策，提供了幾個可以直接抄的具體條款：

  • 預算耗盡時：停止所有變更與發布，僅放行 P0 問題與安全性修補。
  • 單一事故若消耗掉四週預算的 20% 以上，就必須產出事後檢討報告， 且報告中至少要有一個 P0 級行動項。
  • 政策要寫明爭議升級路徑 — 範例中一路可升級到 CTO 裁決。
為什麼「升級路徑」不能省

錯誤預算政策真正被考驗的時刻，是產品部門非常想在預算已耗盡時發布某個功能。 如果政策沒有事先寫好誰有權裁決，那一刻它就會變成一場靠職位高低決定的角力 — 而政策本身也就名存實亡了。

燃燒率告警 (Burn Rate Alerting)

不要對「SLO 已違反」告警 — 那太晚了。要對消耗速度告警：

燃燒率 = 目前錯誤率 / 允許錯誤率

燃燒率 = 1   →  剛好在 28 天末用完預算（健康）
燃燒率 = 14.4 →  2 小時就會燒掉 28 天預算的 2% （緊急，叫人起床）
燃燒率 = 6    →  6 小時燒掉 5%（重要，開工單）

用多重時間窗 (multi-window, multi-burn-rate) 組合告警， 可以同時做到「嚴重問題快速通知」與「輕微抖動不吵醒人」。這是現代告警設計的標準做法。

2.3 瑣務 — 需要被消滅的東西

瑣務 (Toil) 在 SRE 中有非常嚴格的定義，不是「我不喜歡的工作」。 一項工作符合以下特徵越多，越算是瑣務：

隨規模線性成長O(n) with service growth最致命的一項：流量翻倍，工作量也翻倍
為什麼瑣務是頭號敵人

「隨規模線性成長」意味著這份工作永遠追不上業務成長，最終必然導致團隊崩潰或無限擴編。 SRE 的核心任務就是把 O(n) 的維運成本壓成 O(1)。
注意：瑣務不等於「壞工作」。少量瑣務是正常的、甚至有療癒效果；問題出在它佔比失控（超過 50%）。

消滅瑣務的階梯：手動操作 → 寫成文件（Runbook）→ 寫成腳本 → 自我修復系統 → 從架構上根除。 最高境界不是把它自動化，而是讓它不再需要發生。

參考基準

Google 自己實測的 SRE 瑣務佔比：平均約 33%，各團隊分布在 0% 到 80% 之間。 換句話說，連 Google 都沒有把它壓到零 — 重點是持續量測它、並讓它保持在 50% 以下。

階段 2 驗收

你能為一個真實服務（哪怕是你自己的側專案）寫出一份完整的 SLO 文件： 定義 2–3 個 SLI、訂出 SLO 與時間窗、算出錯誤預算、設計燃燒率告警門檻、寫出錯誤預算政策。 並且你能解釋：為什麼你選了這些 SLI 而不是 CPU 使用率。

階段 2 告訴你「該量什麼」，階段 3 告訴你「怎麼量得到」。沒有可觀測性，SLO 只是一張紙。

3.2 遙測三支柱 (The Three Pillars of Telemetry)

指標 Metrics

隨時間變化的數值聚合。成本低、可長期保存、適合告警與趨勢。 缺點：無法回答「這一個特定請求發生什麼事」。

日誌 Logs

離散的事件記錄。細節最豐富，適合事後鑑識。 缺點：量大、貴、難以聚合。應採用結構化日誌 (structured logging, 通常是 JSON)。

追蹤 Traces

一個請求穿越多個服務的完整路徑與各段耗時。 微服務架構下定位「慢在哪一環」的唯一有效手段。

三者靠關聯發揮威力：從一個異常的 SLO 圖表（指標）→ 鑽取到該時段的慢請求（追蹤）→ 查看該請求的錯誤細節（日誌）。 這條路徑能不能一鍵打通，是可觀測性平台成熟度的真正指標。

3.3 四大黃金訊號 (The Four Golden Signals)

如果你只能監控四件事，就監控這四件。這是 Google SRE 提出的、面向使用者的監控起手式：

訊號英文量什麼陷阱
延遲Latency處理一個請求所需的時間必須區分成功與失敗請求的延遲 — 快速失敗會讓平均延遲變好看
流量Traffic系統承受的需求量（QPS、頻寬、並發連線）不同服務的「流量」定義不同
錯誤Errors失敗請求的比率要包含隱性失敗：HTTP 200 但內容錯誤、或違反延遲承諾
飽和度Saturation系統中最受限的那項資源有多滿最難量測；系統通常在遠未達 100% 使用率前就開始劣化，所以要看佇列長度而非單看使用率
書中兩個值得記住的提醒

1. 延遲一定要區分成功與失敗請求來看 — 原文的說法是 "a slow error is even worse than a fast error!"（一個慢的錯誤，比一個快的錯誤還糟）。 快速失敗會把平均延遲拉得很好看，掩蓋真正的問題。
2. 延遲上升往往是飽和度的領先指標 ("Latency increases are often a leading indicator of saturation")。 在資源使用率還沒觸頂時，延遲就會先告訴你系統快撐不住了。

兩個互補的檢查方法

  • USE 方法 (Utilization, Saturation, Errors) — 由 Brendan Gregg 提出， 針對資源（CPU、記憶體、磁碟、網卡）。用於「機器層」的排查：對每一項資源檢查使用率、飽和度、錯誤。
  • RED 方法 (Rate, Errors, Duration) — 針對服務。 用於「請求層」的排查：每個服務量測請求速率、錯誤率、耗時分布。是微服務監控的預設範本。
怎麼選

USE 由下往上（我的機器怎麼了），RED 由上往下（我的使用者怎麼了）， 四大黃金訊號是兩者的交集加上流量。實務上：對服務用 RED，對資源用 USE，對 SLO 用黃金訊號。

3.4 告警設計 — 比監控本身更難

告警疲勞是可靠性的頭號殺手

當工程師開始忽略告警，你的監控系統就等於不存在。而且更糟 — 它給了你虛假的安全感。

告警的鐵律：

  • 每一則會叫醒人的告警，都必須是「緊急、重要、且可採取行動」的。三者缺一，就不該呼叫。
  • 對症狀告警，不要對原因告警 (Alert on symptoms, not causes)。 「使用者的請求失敗率超標」是症狀（該告警）；「某台機器 CPU 90%」是原因（不該直接叫人 — 也許它本來就該滿）。
  • 以 SLO 為告警基礎。用燃燒率告警取代靜態閾值告警，能大幅減少誤報。
  • 區分呼叫 (Page)、工單 (Ticket)、 日誌 (Log) 三種嚴重度，只有第一種能在半夜響。

階段 4 — 基礎設施與雲端Stage 4 — Infrastructure & Cloud

從「一台機器」進入「一群機器」。這是 SRE 工作的實際場域。

4.1 雲端運算基礎

  • 服務模型 — IaaS / PaaS / SaaS 的邊界，以及共同責任模型 (Shared Responsibility Model)：雲商負責什麼、你負責什麼
  • 核心資源 — 運算 (Compute)、儲存 (Object / Block / File Storage)、網路 (VPC、子網路、安全群組)、託管資料庫
  • 可用區與地區 (Availability Zone / Region) — 故障域 (Failure Domain) 的實體邊界，是所有高可用設計的基礎
  • 身分與存取管理 (Identity and Access Management, IAM) — 最小權限原則
  • 成本管理 (FinOps) — 可靠性與成本是一體兩面，SRE 往往也是成本的把關者

工具／平台：AWS、Google Cloud (GCP)、Azure。學一家學透，其餘觸類旁通。 另可參考各雲商的架構良好架構框架 (Well-Architected Framework) 的可靠性支柱，那是官方整理的設計檢查清單。

4.2 基礎設施即程式碼 (Infrastructure as Code, IaC)

核心思想

基礎設施的狀態應該被宣告在版本控制的檔案裡，而不是存在於某個人的記憶或 Console 的點擊歷史中。 這讓基礎設施可審查、可回溯、可重建 — 也讓「重建一個一模一樣的環境」從三天變成三十分鐘。

必須理解的概念

  • 宣告式 vs 命令式 (Declarative vs Imperative) — 宣告「我要什麼結果」而非「怎麼一步步做」。這是雲原生的核心心智轉換。
  • 冪等性 (Idempotency) — 執行一次跟執行十次結果相同
  • 狀態管理 (State Management) — Terraform 的 state 檔為何存在、為何要遠端存放與加鎖
  • 配置漂移 (Configuration Drift) — 實際狀態偏離宣告狀態，以及如何偵測
  • 不可變基礎設施 (Immutable Infrastructure) — 更新即替換，而非就地修改。「寵物 vs 牲畜」(Pets vs Cattle) 的比喻

4.3 容器化 (Containerization)

容器不是輕量虛擬機。它是一個被 Linux 核心的 namespace（隔離視野）與 cgroup（限制資源）圈起來的普通行程。 理解這一點，你才能理解為什麼容器裡的 top 可能顯示宿主機的 CPU、為什麼 PID 1 的訊號處理很特別。

  • 映像檔分層 (Image Layers) 與 OCI 標準
  • 多階段建置 (Multi-stage Build)、映像檔瘦身與安全掃描
  • 容器內的 PID 1 問題 — 訊號轉發與殭屍行程回收
  • 資源限制 — CPU throttling 與 OOM kill 在容器中的表現

工具：Docker、containerd、Podman、BuildKit、Trivy／Grype（漏洞掃描）、Harbor／ECR／GAR（映像檔倉庫）。

階段 4 驗收

你能用 Terraform 從零建出一個跨可用區的環境（VPC、子網路、負載平衡器、運算節點）， 整份設定放在 Git 中，且整個環境可以完整銷毀再重建。你也能解釋 state 檔為什麼不能放在本機。

階段 5 — 分散式架構與 KubernetesStage 5 — Distributed Architecture & Kubernetes

現代 SRE 的主戰場。分散式架構 (Distributed Architecture) 是問題的來源， Kubernetes (K8s) 是目前業界管理它的主要工具。

5.1 分散式系統的基本困難

在寫任何 YAML 之前，先接受這些殘酷事實：

  • 分散式運算的謬誤 (Fallacies of Distributed Computing) — 網路不可靠、延遲不為零、頻寬非無限、網路不安全、拓撲會變、管理員不只一個、傳輸成本不為零、網路不同質。每一條都是事故的來源。
  • CAP 定理 (Consistency, Availability, Partition tolerance) — 網路分區發生時，只能在一致性與可用性之間擇一。實務上「P 不可選」，所以真正的問題是 CP 還是 AP。
  • 部分失敗 (Partial Failure) — 單機程式非成即敗， 分散式系統會處在「不知道成功了沒」的第三態（逾時）。這催生了冪等性與重試的設計需求。
  • 共識 (Consensus) — Raft / Paxos 的存在理由：讓一群機器對某件事達成一致。 你不需要實作它，但要知道 etcd、ZooKeeper 依賴它，以及它為什麼需要多數節點存活（quorum）。
  • 時間不可信 — 時鐘漂移、NTP、為什麼不能用機器時間戳排序分散式事件（→ 邏輯時鐘）

5.2 韌性設計模式 (Resilience Patterns)

必須理解的失效模式：級聯故障 (Cascading Failure)

一個節點過載 → 它變慢或掛掉 → 流量被導向其餘節點 → 其餘節點也過載 → 全體崩潰。 更惡劣的是重試風暴：客戶端的重試在系統已經過載時，讓負載再翻倍。
對策：限流 + 負載卸除 + 帶抖動的指數退避 + 重試預算 (retry budget) + 斷路器。 而且 — 恢復時要小心「驚群」，冷快取重啟往往比原故障更致命。

5.3 Kubernetes — 為什麼是它

Kubernetes 的本質是一個宣告式的、以控制迴圈驅動的叢集狀態管理器：

你宣告「期望狀態」 控制器持續比對 系統趨向期望狀態 (Desired State) ────▶ (Control Loop) ────▶ (Actual State) YAML 觀察 → 比對 → 修正 │ ▲ │ └─────────────────── 持續調和 (Reconciliation) ────┘

這個「調和迴圈」(Reconciliation Loop) 是理解 K8s 一切行為的鑰匙 — 包括為什麼你刪掉的 Pod 會自己長回來，以及為什麼 GitOps（階段 6）能成立。

  • 排程控制 — 親和性 (Affinity)、反親和性 (Anti-Affinity)、Taint／Toleration、 拓撲分佈約束 (Topology Spread Constraints) — 跨可用區高可用的關鍵

  • 擴充機制 — CRD 與操作器模式 (Operator Pattern)：把維運知識寫成控制器

階段 6 — 自動化與交付Stage 6 — Automation & Delivery

絕大多數的線上事故源自變更。因此「怎麼安全地變更」是 SRE 的核心命題，而不是開發團隊的家務事。

6.1 持續整合與持續交付 (CI/CD)

  • 持續整合 (Continuous Integration, CI) — 頻繁合併到主幹，每次合併都自動建置與測試
  • 持續交付 (Continuous Delivery, CD) — 每個通過測試的版本都隨時可以上線
  • 持續部署 (Continuous Deployment) — 通過測試就自動上線，無人工關卡
  • 建置的可重現性 (Reproducible Build)、 物料清單 (SBOM) 與供應鏈安全
  • 發布工程 (Release Engineering) 四原則： 自助服務模式、追求高速度、密封建置 (Hermetic Build)、政策與程序的強制執行

6.2 GitOps

核心思想

Git 儲存庫是系統期望狀態的唯一真相來源，由叢集內的代理程式持續拉取並自動調和實際狀態。 部署不再是「推送一個指令」，而是「合併一個 PR」。這讓每一次變更都自帶審查、稽核與回滾（git revert）。

GitOps 的四項原則：宣告式 (Declarative)、版本化且不可變 (Versioned and Immutable)、 自動拉取 (Pulled Automatically)、持續調和 (Continuously Reconciled)。 注意最後一項 — 它同時解決了配置漂移：有人手動改了叢集，系統會自己改回來。

6.3 漸進式交付 (Progressive Delivery)

目標是把變更的爆炸半徑 (Blast Radius) 控制在可接受範圍。

階段 7 — 事件管理與待命Stage 7 — Incident Response & On-Call

前面所有階段都是為了「少出事」。這一階段處理的是「出事之後」— 而這正是 SRE 專業度最被檢驗的時刻。

7.1 待命 (On-Call)

待命是 SRE 的責任，但健康的待命制度是有設計的，不是「大家輪流受苦」：

  • 可持續性 — 待命期間的告警量應該低到讓人能兼顧正常工作與睡眠。 Google SRE 給出的量化上限是每 12 小時輪班最多 2 起事故 （推導依據：完整處理一起事故 — 含調查、根因分析、修復、撰寫事後檢討 — 約需 6 小時）。 註：SRE Book 第 1 章的表述略有出入，寫作「每 8–12 小時輪班最多兩起事件」。 超過這個量，代表要修的是系統或告警，不是人的耐受度。
  • 補償 — 待命必須有明確的時間補休或金錢補償，否則制度會靜靜地崩壞。
  • 主／副輪值 (Primary / Secondary) — 主值班漏接時的安全網。
  • 交接 (Handoff) — 每次輪班結束要有明確的狀態交接。
  • 值班手冊 (Runbook / Playbook) — 每一則會呼叫人的告警，都必須連結到一份說明「這是什麼、影響誰、先做什麼」的文件。 研究顯示，有值班手冊能大幅降低平均修復時間。

7.2 事故管理 (Incident Management)

事故中最大的風險不是技術，是混亂

常見失敗模式：所有人都在查同一件事、沒有人在對外溝通、有人在未告知的情況下改了生產環境、 指揮權不明導致決策癱瘓。結構化的角色分工是解方。

源自消防體系的事故指揮系統 (Incident Command System, ICS) 角色劃分：

角色英文職責
事故指揮官Incident Commander (IC)做決策、分派任務、維持全局視野。IC 不動手修 — 一動手就失去全局。
維運主管Operations Lead (OL)實際執行修復動作的人，唯一被授權變更系統者
溝通主管Communications Lead (CL)對內外通報進度，隔絕干擾讓技術人員專心
計畫主管Planning Lead記錄時間軸、追蹤待辦、處理交接與長期事故的輪班

事故處理流程

  1. 偵測 (Detect) — 告警觸發或使用者回報
  2. 分級 (Triage) — 判定嚴重度 (Severity, SEV1–SEV4)，決定要動員多少人
  3. 宣告 (Declare) — 明確宣布「這是事故」，指定 IC，開專屬溝通頻道。寧可過度宣告，也不要拖延
  4. 止血 (Mitigate) — 優先恢復服務，而不是找出根因。回滾、切流量、擴容、關閉功能旗標
  5. 解決 (Resolve) — 確認 SLI 回到正常水位
  6. 檢討 (Review) — 撰寫事後檢討報告
關鍵心法

止血優先於診斷 (Mitigate before you diagnose)。使用者不在乎根因，只在乎服務有沒有恢復。 找根因是事後檢討的工作，不是事故當下的工作。

7.3 事後檢討 (Postmortem)

SRE 文化中最重要、也最容易被做壞的一項實踐。

免責的事後檢討 (Blameless Postmortem)

核心假設：每個人在當下都基於自己掌握的資訊、以合理的意圖做出了最好的判斷。 因此檢討的對象是系統與流程，不是個人。
如果一個人「按錯按鈕」就能造成大規模故障，問題在於那個按鈕不該這麼容易按錯 — 缺少確認機制、缺少權限隔離、缺少自動化。
反面警訊：一旦開始追究責任，工程師就會隱藏錯誤與細節，而你將永遠失去改善系統所需的真實資訊。

一份合格的事後檢討報告應包含

  • 摘要與影響 — 影響了誰、多久、多嚴重（量化：燒掉多少錯誤預算、多少請求失敗）
  • 時間軸 (Timeline) — 從起因到恢復的關鍵時間點，含偵測與回應延遲
  • 根因分析 (Root Cause Analysis) — 注意：複雜系統的事故通常有多重成因，「唯一根因」往往是過度簡化
  • 觸發因素與偵測方式 — 為什麼發生、我們怎麼知道的（是使用者告訴我們的嗎？那監控有缺口）
  • 做對了什麼／哪裡走運了 — 保存有效的做法，也標記出僥倖之處
  • 行動項 (Action Items) — 必須有負責人、期限、追蹤編號。沒有追蹤的行動項等於沒有檢討。

階段 8 — 進階可靠性工程Stage 8 — Advanced Reliability Engineering

從「處理已發生的問題」進化到「主動找出還沒發生的問題」。

8.1 容量規劃 (Capacity Planning)

  • 需求預測 (Demand Forecasting) — 有機成長（自然流量成長）與非有機成長（行銷活動、新功能上線）要分開估
  • 負載測試 (Load Testing) 的四種類型 — 基準測試 (Baseline)、壓力測試 (Stress，找斷點)、浸泡測試 (Soak，找記憶體洩漏)、尖峰測試 (Spike)
  • 擴展性建模 — Amdahl 定律與通用擴展定律 (USL)：為什麼加機器的效益會遞減甚至變負
  • 排隊理論的直覺 (Queueing Theory) — Little's Law； 系統使用率超過約 80% 後，延遲會以非線性方式暴增。這是「不要把資源用滿」的數學理由。
  • 成本與可靠性的權衡 — 多留 50% 冗餘的成本，是否高於停機的成本

8.2 混沌工程 (Chaos Engineering)

定義

混沌工程是在系統上進行實驗的學科，目的是建立對系統在生產環境中抵禦動盪狀況能力的信心。
"Chaos Engineering is the discipline of experimenting on a system in order to build confidence in the system's capability to withstand turbulent conditions in production."

它不是「隨機弄壞東西」。它是一套有假說、有對照、有爆炸半徑控制的科學方法：

  1. 定義系統的穩態 (Steady State) — 用可量測的業務指標（如訂單成功率），不是機器指標
  2. 假設穩態在實驗組與對照組都會維持
  3. 注入真實世界會發生的事件 — 機器當機、網路延遲、依賴逾時、磁碟寫滿、憑證過期
  4. 試圖推翻假說；穩態被打破的地方就是你的脆弱點

官方列出的五項進階原則 (Advanced Principles)：

原則英文重點
圍繞穩態行為建立假說Build a Hypothesis around Steady State Behavior 混沌實驗是驗證系統「確實能運作」，而不是驗證它「如何運作」；焦點在可量測的輸出，不是內部細節
變動真實世界的事件Vary Real-world Events 只注入真的會發生的事件（機器當機、磁碟故障、網路中斷、流量尖峰），並依影響或頻率排序
在正式環境中執行實驗Run Experiments in Production 取樣真實流量是唯一能可靠捕捉請求路徑的方式 — 測試環境的行為不等於正式環境

前置條件

不要在階段 3（可觀測性）與階段 7（事故流程）成熟之前做混沌工程。 如果你看不見系統的狀態，你只是在製造事故，不是在做實驗。

工具：Chaos Mesh、LitmusChaos、Gremlin、AWS Fault Injection Service、Toxiproxy（網路故障注入）。

8.3 效能工程 (Performance Engineering)

  • 剖析 (Profiling) — CPU、記憶體、鎖競爭；火焰圖 (Flame Graph) 的判讀
  • 持續剖析 (Continuous Profiling) — 在生產環境長期低開銷取樣（Pyroscope、Parca）
  • 尾端延遲 (Tail Latency) — 當一個請求要扇出到 100 個後端，p99 就變成了實質上的常態。對策：對沖請求 (Hedged Request)、分層取消。
  • 資料層 — 索引、查詢計畫、連線池、N+1 問題、快取策略與快取雪崩 (Cache Stampede)

8.4 災難復原 (Disaster Recovery, DR)

階段 8 驗收

9.2 DORA 四大關鍵指標 (DORA Four Keys)

由 DevOps Research and Assessment 研究計畫提出，用來衡量軟體交付表現。 SRE 常用它來證明「更快」與「更穩」不是取捨關係 — 高績效團隊在兩邊同時勝出。

名稱已更新 — 別再用舊稱

DORA 官方頁面現行列出的是五個指標，且名稱與早期廣為流傳的版本不同： 第四項已不再叫 "Time to Restore Service" 或 MTTR，而是 Failed deployment recovery time； 第三項官方寫法是 Change fail rate（不是 change failure rate）； 並新增了第五項 Deployment rework rate。分組也改為吞吐量 / 不穩定性，而非舊的「速度 / 穩定」。

9.3 非技術能力

技術寫作

事後檢討、設計文件、Runbook、SLO 文件。寫作品質直接決定你的影響力半徑 — 你不在場時，只有文件替你說話。

危機溝通

在壓力下清晰、簡短、誠實地更新狀態。對高階主管要講影響與時程，不要講技術細節。

不靠職權的影響力

SRE 通常無權命令開發團隊。你靠數據（SLO、錯誤預算）與信任推動改變。

風險判斷

知道什麼時候該說「這個風險可以接受」。過度追求可靠性跟不夠可靠一樣有害。

附錄 C — 常見反模式Appendix C — Anti-Patterns

反模式為什麼有害
把 SRE 當成改名的維運團隊沒有工程時間、沒有拒絕權、沒有 SLO — 只是換個名字繼續燒人
追求 100% 可用性成本無上限，且會凍結所有創新；使用者也感受不到
沒有錯誤預算政策的 SLOSLO 破了沒有任何後果，就只是一張漂亮的圖表
對 CPU／記憶體使用率設告警並呼叫人對原因告警而非症狀，製造大量與使用者無關的雜訊
究責式的事後檢討工程師會隱藏資訊，你將永遠拿不到改善系統所需的真相
工具先行、問題後補先導入服務網格再問要解決什麼；複雜度本身就是可靠性的敵人
事故當下堅持先找根因延長使用者受影響時間；止血優先，診斷留給事後
行動項沒有負責人與期限同樣的事故會再發生一次，而且大家都記得上次討論過
可觀測性未成熟就做混沌工程看不見系統狀態時，那不是實驗，只是自己製造事故
Runbook 只存在於某個資深工程師腦中該人一離職或休假，MTTR 立刻暴增
